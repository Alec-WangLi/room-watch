# room-watch M3/M4 基准报告（2026-10-21）

- 对应里程碑：M3 录制/存储收口、M4 推理引擎决策
- 设计：`docs/superpowers/specs/2026-10-21-m3-encoder-m4-benchmark-design.md`
- 结论摘要：
  - **M3**：`h264_mf` 比 avc1 少约 59% 体积、每帧快约 38%，作为 auto 默认；
    nvenc/libx264 更小，但前者依赖显卡、后者是软件编码，不进 auto。
  - **M4**：ONNX Runtime 每帧 CPU 时间少约 31%、p95 延迟低约 45%，
    检测框完全一致，达到切换门槛；本轮**不捆绑**（安装包约 +50MB），
    默认仍 cv2.dnn，待所有者决定是否随包分发。

## 2. M3：编码器对比

命令：

```bash
python -m roomwatch bench-encode --frames 120 --json
```

120 帧、1280×720、10fps、合成画面（有明显运动）：

| 编码器 | 方式 | ms/帧 | MB/分钟 | 120 帧体积 | 相对 avc1 |
|---|---|---:|---:|---:|---:|
| avc1 | cv2（Media Foundation） | 7.4 | 125.4 | 1.849 MB | 基线 |
| mp4v | cv2 | 4.7 | 159.5 | 1.505 MB | +27% |
| MJPG | cv2 | 4.5 | 120.7 | 1.076 MB | -4% |
| h264_nvenc | ffmpeg / NVENC | 5.3 | 32.2 | 0.342 MB | **-74%** |
| h264_mf | ffmpeg / Media Foundation | 4.6 | 51.9 | 0.480 MB | **-59%** |
| libx264 | ffmpeg / 软件 | 5.1 | 19.2 | 0.197 MB | **-85%** |
| h264_qsv / h264_amf | ffmpeg | 不可用 | — | — | Broken pipe |

观察：

- `h264_mf` 在体积和速度上都优于 avc1，且 Media Foundation 在 Windows
  10/11 上普遍可用，因此作为 auto 首选。
- `h264_nvenc` 体积更小，但只有 NVIDIA 显卡可用；作为 auto 第二候选。
- `libx264` 在这台 20 核机器上最快、体积最小，但它是软件编码，
  客户机（N100 一类小主机）上可能明显变慢；不放进 auto，只允许显式配置。
- qsv/amf 在本机没有对应硬件，基准按失败记录，不影响其它项。

## 3. M4：推理引擎对比

命令（各跑 3 次，取中位数；同一合成帧、线程数 2、imgsz 640）：

```bash
PYTHONPATH=build/onnxruntime-libs python -m roomwatch bench-detect \
  --engine cv2,onnxruntime --frames 100 --json
```

| 引擎 | ms/帧（中位） | p50 ms | p95 ms | CPU ms/帧（中位） | 等效 10fps CPU 核 |
|---|---:|---:|---:|---:|---:|
| cv2.dnn（onnx） | 85.7 | 100.1 | 106.3 | 161.2 | 1.61 |
| onnxruntime | 56.0 | 55.8 | 58.0 | 111.7 | 1.12 |

原始三次数值：

- cv2：ms 87.1 / 85.7 / 85.1；p95 107.8 / 104.7 / 106.3；
  CPU ms/帧 164.2 / 161.2 / 158.8。
- onnxruntime：ms 57.0 / 55.9 / 56.0；p95 59.4 / 58.0 / 57.8；
  CPU ms/帧 113.1 / 111.7 / 111.1。
- 两次结果都带 `consistent: true`（命令已内置一致性对比）。

改善幅度（中位数）：

- 墙钟延迟 **-34.7%**（85.7 → 56.0 ms）
- p95 延迟 **-45.4%**（106.3 → 58.0 ms）
- 每帧 CPU 时间 **-30.7%**（161.2 → 111.7 ms）
- 固定 10fps 时等效 CPU 核从约 1.61 降到 1.12

检测一致性：在同一张真实 720p 抓拍上，两套后端的框与置信度完全一致
（(349,264)-(979,707)，conf 0.836），`bench-detect --engine cv2,onnxruntime`
输出的 `consistent` 为 true。

决策：

- 按上游文档的门槛（CPU 或延迟改善 ≥20%），**两项都明显通过**。
- 代价：onnxruntime 约 50MB 依赖，会推高安装包体积；本轮按设计
  **不捆绑、不改变默认引擎**，`detector.engine=onnxruntime` 作为可选路径保留
  （仅当用户自行安装 onnxruntime 时可用）。
- 下一步需要所有者决定是否随包附带；如果附带，建议下一轮单独做体积与
  安装包验证。

## 4. 本机文件源验证（0.2.2 安装后）

摄像头被运行中的监控占用，验证用一张真实 720p 抓拍生成 8 秒视频（轻微平移），
通过 `camera.source` 文件源跑完整 watcher（事件、预录、分段、抓拍、退出收尾）。

| 变体 | 实际编码器 | 第 1 段 MB/分钟 | 第 2 段 MB/分钟 |
|---|---:|---:|---:|
| auto（默认） | h264_mf | 2.1 | 3.3 |
| `ffmpeg_encoder=h264_nvenc` | h264_nvenc | 4.1 | 3.8 |
| `ffmpeg_encoder=libx264` | libx264 | 2.6 | 2.9 |
| ffmpeg 路径不存在 | avc1 | 27.0 | 29.8 |
| `encoder=cv2` | avc1 | 27.0 | 29.8 |

- 同源对比：默认 h264_mf 比 avc1 体积下降约 89–92%（源画面以静止为主，
  绝对值低于合成基准，比例仍成立）。
- 四条路径的 `status.json.video_encoder` 与预期一致；ffmpeg 不可用时
  `video_encoder_error` 为「没有可用的 ffmpeg 编码器」。
- 片段为 H.264 Constrained Baseline / yuv420p，cv2 与 ffmpeg 均可读；
  用 `adelay` 合并静音 wav 后输出同时含 H.264 视频与 AAC 音轨。
- 未触发实时摄像头的陌生人事件（摄像头独占）；事件路径由文件源完整跑通。

## 5. 运行中监控采样

命令（采样已安装的 0.2.1，监控持续运行）：

```bash
python -m roomwatch bench --seconds 60 --interval 1 --json \
  --health "%LocalAppData%\Programs\room-watch\var\state\health.json"
```

结果：

```json
{"count": 60, "cpu_mean": 55.4, "cpu_peak": 64.1, "rss_mean_mb": 235.9,
 "rss_peak_mb": 236.1, "stale_samples": 0, "frames_latest": 24115}
```

本人在场、0.2.1 降频生效时的生产基线：CPU 均值 55.4%、峰值 64.1%，
RSS 约 236MB，无 stale 样本。

## 6. 结论

- M3：编码器切换收口，auto 默认 `h264_mf`，失败回退 cv2；体积下降超过
  验收要求的 40%。
- M4：基准数据支持 ONNX Runtime（每帧 CPU -31%、p95 -45%、检测一致），
  但本轮不改变安装包构成；决策记录在 `CHANGELOG.md` 与交接文档，
  等待所有者决定是否捆绑。
