# room-watch 稳定性、性能与产品化设计

- 日期：2026-10-19
- 状态：待所有者确认
- 适用范围：Windows 桌面版（USB 摄像头 + 本机常开主机）
- 本文不包含实现代码，只描述「要做什么、为什么、边界在哪」

## 1. 背景与意图

room-watch 已经能在 Windows 上完成核心闭环：本机摄像头 → YOLO 人形检测 →
抓拍/录像 → 人脸识别 → 语音播报 + 微信推送。项目已开源（AGPL-3.0），
下载者不止所有者本人。

所有者明确的目标：

1. **稳定性第一**：它必须一直活着，真出事时一定通知到人；功能数量其次。
2. **性能第二**：降低常驻开销（CPU / 内存 / 磁盘），必要时可以更换底层实现。
3. **推送投递层重做**：持久化重试 + 双通道 + 外部心跳，渠道本身保留。
4. **产品化是真实目标**：陌生用户下载安装后应当「装完即忘」，不需要理解
   会话、进程、命令行。
5. **不加深 Windows 专属耦合**：Linux 主机是以后的事，不为此牺牲当前功能，
   但新代码不要把 Windows 细节散落到核心逻辑里。

## 2. 目标 / 非目标 / 反目标

### 目标

- 连续运行 7 天，不出现「无解释的静默退出」；如果退出，必须有原因记录，
  并由投递层通知所有者。
- 任何真实入侵事件至少通过一个已配置渠道送达；积压消息在重启、断网恢复后
  继续投递，不因队列满而静默丢弃。
- 整机断电、断网、全部进程死亡时，仍能由外部服务发现「心跳消失」并提醒。
- 待机与事件时的 CPU、内存、磁盘开销有可重复的基准数据；优化必须用数据证明。
- 新用户安装后不需要命令行即可完成：摄像头选择、本人注册、推送测试、
  外部心跳配置，并确认系统真的在工作。
- 现有配置、数据目录、升级路径向后兼容。

### 非目标（本阶段明确不做）

- Linux 移植、Docker 化、RTSP 多摄像头、远程实时画面、手机 App。
- 云端存储或云端推理；视频/照片不经过任何自建云。
- 重写架构；继续沿用现有模块边界（watcher / rules / recorder / identity /
  notifier / guardian 等）。
- 为升级模型而升级模型；YOLOv8n → YOLO11n 这类收益很小的替换不在本阶段。
- 英文界面与英文文档（开源用户如果需要，作为后续独立事项）。
- 代码签名证书（SmartScreen 提示按文档说明处理，不在本阶段采购）。

### 反目标（即使「能跑」也算失败）

- 要求用户去某个云端或某个开发工具里「新建会话」才能后台运行。
- 为了性能引入一个让安装包膨胀数倍、且用户机器不一定支持的强制依赖。
- 只依赖单一推送渠道；渠道失效时系统表现为「安静地失联」。
- 用「崩了就重启」掩盖根因，重启历史不可见、不通知。
- 把房间画面或人脸特征上传到任何第三方（用户显式配置的推送渠道除外）。
- 破坏 `data/` 隐私边界，或把凭据写进入库文件。

## 3. 约束

- Windows 10/11 x64；免管理员安装；随包附带 Python 运行时。
- **USB 摄像头只能在用户登录会话中采集**：Windows 服务运行在 Session 0，
  DirectShow / Media Foundation 都没有受支持的摄像头采集路径。因此采集进程
  不能做成 Windows 服务，安装器必须注册「登录时静默启动」。
- 摄像头设备独占：同一时刻只能有一个采集进程。
- **常驻启动不能假定计划任务一定可用**：所有者的机器上 `schtasks.exe`
  在系统黑名单里（见 `AGENTS.md` I.7）。autostart 必须定义降级路径
  （HKCU Run + VBS），安装器还要清理旧入口，避免新旧两套自启同时拉进程。
- 现有版本纪律：前两位是已批准基线，未经所有者同意只动修订号；
  本设计涉及的发布都应是小版本修订。
- AGPL-3.0 与 YOLO 权重许可保持不变。
- 所有新增测试必须离线可跑，不依赖真实摄像头与网络。

## 4. 已定决策（来自所有者）

| 决策 | 内容 |
|---|---|
| 产品形态 | 不变：Windows 常开主机 + 本机摄像头，事件驱动 |
| 优先级 | 稳定性 > 性能 > 功能数量 |
| 底层实现 | 允许更换，只要能用数据证明更好 |
| 推送 | 持久化重试 + 双通道 + 外部心跳；现有渠道保留 |
| 产品化 | 是；开源下载者要能装完即用 |
| Linux | 暂不做，但不要加深 Windows 耦合 |

## 5. 现状问题（设计要解决的）

1. Watcher 每 30–63 分钟静默退出一次，根因未知；目前只靠 guardian 拉起兜底，
   重启原因、退出码、崩溃栈都没有落盘。
2. Guardian 只守护 watcher，gallery 挂了需要人工处理。
3. videopush 使用内存队列，队列满即丢弃；断网期间的通知会丢。
4. 只有企业微信机器人能发图+视频；其余渠道只有文字。
5. 没有任何「整机失联」检测：机器断电、断网、全部进程死掉时，用户只会
   看到「没有消息」，无法区分「平安」和「监控已死」。
6. 录像在本人长时间在房间时持续写入，约 65.6 MB/分钟，20GB 上限约 5 小时。
7. 没有性能基准；无法判断优化是否有效。
8. 安装后缺少「真的在工作」的闭环验证；异常只写日志，陌生用户看不懂。

## 6. 设计

### 6.1 稳定性与可观测性（先于修复）

目的：在动任何「修复」之前，先让「为什么退出」变成可回答的问题。

- **启动即装崩溃钩子**：`faulthandler.enable()` 写入
  `var/logs/watcher-fault.log`；`sys.excepthook`、`threading.excepthook`
  记录未捕获异常；`atexit` 记录退出原因；主循环外层捕获所有异常并以
  约定退出码退出。
- **退出码约定**（示意，构建者可调整）：
  `0` 正常停止、`2` 配置错误、`3` 摄像头不可用、`4` 模型加载失败、
  `5` 未处理异常、`6` 心跳停滞被守护进程终止。
- **健康快照** `var/state/health.json`：每秒或每帧更新一次，至少包含
  `loop_seq`、`started_at`、`last_frame_at`、`last_inference_at`、
  `consecutive_errors`、`camera_reopens`、`rss_mb`、`cpu_pct`、
  `pending_outbox`、`last_push_success_at`。
- **主循环停滞检测**：独立看门线程检查 `loop_seq` 是否在
  `health.stall_seconds`（默认 120 秒，可配置）内增长；停滞时把
  所有线程栈写入日志，并标记为停滞。是否让进程主动退出交给构建者决定，
  但必须让 guardian 能据此重启并记录原因。
- **结构化日志**：保留现有日志文件，新增轮转（大小 + 份数），
  关键事件（启动、停止、摄像头重连、每阶段异常、推送结果）用固定字段，
  便于陌生用户导出。
- **重启历史**：guardian 写 `var/state/guardian_history.jsonl`，
  每条包含时间、退出码、运行时长、最后一次健康快照摘要。
- **诊断包**：新增 `rw diag`，生成一个 zip：日志、脱敏后的
  `config.local.yaml`（凭据只留掩码）、`health.json`、系统信息、
  `doctor` 输出、最近事件摘要。默认写 `var/diag/`，供用户提 issue。
- **可选原生崩溃转储**：Windows Error Reporting LocalDumps 需要注册表与
  权限，不设为默认；在文档中说明如何开启。

### 6.2 守护与自愈

- **两层守护，允许降级**：
  1. 首选计划任务（登录时触发）启动 guardian，并启用「失败后重启」；
  2. 计划任务不可用或被安全策略拦截时（所有者的机器即如此），
     降级为 HKCU Run + VBS 隐藏启动；此时没有系统级重启，
     由 guardian 自身承担全部重启职责；
  3. guardian 守护 watcher 与 gallery，二者都由它拉起。
- **升级迁移**：安装器必须识别并清理旧版 Run 入口，避免「旧 Run 值 +
  新计划任务」同时存在，导致两个 guardian 抢摄像头。
- **静默启动**：无论走哪条路径，都必须零控制台闪窗；
  不要求用户保持任何窗口。控制面板（GUI）仍为可选组件。
- **启停语义（必须明确）**：
  - 新增期望状态（`var/state/desired_state.json` 或等价物）：
    `running` / `paused`；
  - GUI「停止监控」与 `rw stop`：写 `paused`，走现有优雅停止协议；
    guardian 看到 `paused` 不重启，且不发送「已恢复」通知；
  - GUI「启动监控」与 `rw start`：写 `running`；若 guardian 已在运行，
    让它启动/恢复 watcher，而不是另起一个进程；
  - guardian 是唯一的进程启动者，GUI 不再直接 spawn watcher；
  - 用户主动暂停时，按配置发送一条「监控已暂停」通知，并停止外部心跳；
    外部服务在宽限期后告警属于预期行为，文档需说明；
  - 只有因崩溃而重启才发送「监控已恢复，上次退出原因：…」。
- **guardian 职责扩展**：
  - 同时监督 watcher 和 gallery；
  - 记录退出码与重启原因；
  - 指数退避重启（示例：2s → 10s → 30s → 60s，上限 5 分钟）；
  - 统计窗口内重启次数（例如 10 分钟 3 次），达到阈值后通过投递层
    发送「反复崩溃」告警，而不是无限静默重试；
  - 通过 `health.json` 判断「进程活着但卡死」，必要时优雅停止后重启；
  - 保留单实例锁与优雅停止协议（`stop.request`）。
- **启动自检**：watcher 启动后检查摄像头可打开、模型可加载、磁盘可写、
  `data/` 可写、推送配置完整；结果写入 health 与日志，GUI 首屏可见。
  失败不静默：至少写入状态文件，按配置发送通知。
- **恢复通知**：guardian 在重启成功后（且配置了推送）发送一条
  「监控已恢复，上次退出原因：…」的短消息，避免用户误以为一直正常。
- **不采用 Windows 服务承载采集**：这是平台限制，不是实现偏好；
  文档与安装器都要明确说明「电脑需要保持登录状态（可自动登录 + 锁屏）」。

### 6.3 通知投递层

#### 6.3.1 持久化发件箱

- 使用 SQLite 表 `outbox`（可与 events.db 同库或独立库，构建者决定），
  字段至少包含：`id`、`event_id`、`channel`、`kind`
  （text/image/video）、`payload`（JSON 或媒体路径）、`created_at`、
  `attempts`、`next_attempt_at`、`status`、`last_error`、`dedupe_key`。
- 生成告警时先写入 outbox，再由投递 worker 发送；主循环不等待网络。
- 状态机：`pending → sending → delivered | failed_permanent | expired`。
- **重试**：指数退避 + 抖动（示例：5s、30s、2m、10m、1h、6h，上限 24h）；
  区分「可重试」（超时、网络错误、5xx、限流）与「永久失败」
  （配置错误、4xx 凭据无效），永久失败不无限重试，并在 GUI 中显著提示。
- **重启恢复**：进程启动时扫描 pending/sending，恢复投递；`sending`
  超时未确认的项回到 pending，避免卡死。
- **去重**：`dedupe_key = event_id + channel + kind`；重试不得产生重复消息。
- **容量与过期**：媒体文件放 `var/outbox/`，默认 7 天过期；设置总容量上限
  （例如 2GB）。达到上限时先丢最旧的**已过期或视频**项，并写一条
  「队列溢出」诊断记录；文字告警优先级最高，不允许被视频挤出。
- **优先级**：文字 > 图片 > 视频；视频压缩与上传是独立任务，不阻塞前两者。

#### 6.3.2 多渠道扇出

- 配置改为渠道列表（`notify.channels`），每个渠道可独立启用/禁用，
  并可按事件类型过滤。
- 保留 `wecom_bot`、`wxpusher`、`serverchan`。
- 新增**通用 webhook** 渠道：POST JSON（字段固定：事件类型、时间、
  是否本人、文字、媒体是否存在），便于接入 ntfy / Gotify / Bark /
  Telegram 代理 / 自建服务。媒体是否内联由构建者按大小与渠道能力决定。
- 「双通道」落地为：GUI 在只配置一个渠道时给出明确警告，
  但**不强制**；所有者自己的配置使用两个渠道。
- 渠道健康：记录每个渠道最近一次成功时间与最近错误，GUI 可见；
  配置保存后自动发测试消息（已有能力，复用）。
- **事件分级与过滤**：
  - `critical`：反复崩溃、监控恢复、启动自检失败、队列溢出、
    摄像头丢失、外部心跳连续失败。`critical` 不受渠道过滤影响，
    发往所有已启用渠道；只允许通过「禁用整个渠道」来停止接收。
  - `event`：陌生人/人员事件、抓拍、录像，可按渠道过滤。
  - `digest`：每日在线心跳等，可单独开关。
  - 若所有渠道都被禁用，GUI 必须持续显示「告警不会送达」。

#### 6.3.3 外部心跳（死手开关）

- 新增 `monitor.heartbeat_url`（成功 ping，可留空）、
  `monitor.heartbeat_fail_url`（可选）、`monitor.heartbeat_start_url`（可选）。
  由 **guardian** 按 `monitor.heartbeat_interval_seconds`（默认 300 秒）
  发送 GET/POST。**不做服务商特定的 URL 后缀拼接**，用户显式填写完整 URL。
  healthchecks.io 示例：成功 `https://hc-ping.com/<uuid>`，
  失败 `https://hc-ping.com/<uuid>/fail`，启动 `.../start`。
  Uptime Kuma 这类只有 push URL 的服务：失败时停止 ping，
  由外部服务在宽限期后告警。
- 语义：
  - watcher 与 gallery 健康 → 正常 ping；
  - watcher 反复崩溃或无法恢复 → 若配置了 fail URL 就 ping 它，
    未配置则停止 ping，让外部服务在宽限期后告警；
  - 整机断电/断网/guardian 也死 → 没有 ping，外部服务在宽限期后告警。
- 推荐 healthchecks.io（免费额度）或自建 Healthchecks / Uptime Kuma；
  ntfy 只作为推送渠道，不作为心跳服务。
- 心跳只包含存活信息，不包含画面、人脸或配置；URL 中的 token 视为凭据，
  按现有掩码规则处理。
- GUI 提供「测试心跳」按钮，并显示最近一次成功时间。
- 心跳接口只是普通 HTTP，可接任何兼容服务，不绑定任何一家。
- 若未配置外部心跳，GUI 必须明确提示：「整机失联时无法通知」。

### 6.4 性能与存储

#### 6.4.1 基准先行

- 新增基准工具（`rw bench` 或 `scripts/bench.py`），至少测量：
  - 空闲 10 分钟：CPU 均值/峰值、RSS、摄像头读取失败次数；
  - 事件 5 分钟：CPU、RSS、推理延迟 p50/p95、编码 CPU、磁盘写入速率；
  - 不同分辨率（720p/1080p）与检测间隔下的对比。
- 结果写入 `var/bench/<时间>.json`，并在 `docs/` 记录一次基线报告。
- **决策门**：任何推理引擎/编码器变更，必须在同一台机器上相对基线有
  可重复的明显收益（建议 ≥20% CPU 或延迟下降），且识别效果不回退。

#### 6.4.2 检测与推理（按测量结果决定）

- 抽象检测后端：`detector.engine = auto | cv2 | onnxruntime`，
  并允许 ONNX Runtime 选择 CPU / OpenVINO / DirectML / CUDA（若用户自备）。
- 默认安装包只保留现有 cv2.dnn 路径；只有当基准证明 ONNX Runtime CPU
  明显更省时，才考虑随包附带（注意安装包体积）。
- 不默认捆绑 CUDA/cuDNN；GPU 加速作为可选的「高级安装」或文档步骤，
  由用户自行决定。GPU 不可用时必须无损回退到 CPU。
- 可调项：输入尺寸（320/416/640）、推理间隔、量化（INT8）、
  `intra_op_threads`。默认值以基准结果为准。
- **资产约束**：当前 `models/yolov8n.onnx` 是固定 640 形状；在重新导出
  320/416 变体之前，`detector.input_size` 只允许 640。M4 可以用同一份
  权重导出额外形状，但是否随包分发由基准与安装包体积决定。
- 模型本身不作为本阶段优化手段。

#### 6.4.3 采集与录像

- **录制策略**（产品行为变更，按以下默认值）：
  - 事件录像有最大时长（默认 3 分钟）；到达上限后若人仍在，经过冷却
    再开新片段，避免一个无限长文件；
  - 「本人在场」定义为 **Windows 键鼠空闲时间低于现有
    `behavior.skip_when_user_active` 的阈值**，不是人脸识别结果；
    同一在场会话内从第一次事件开始计时，累计录像不超过 10 分钟，
    新事件不重置计时；本人离开（空闲超过阈值）并经过冷却后计时重置。
    人脸识别的 `on_owner=skip` 继续独立生效；
  - 预录仍保留，默认 8 秒；
  - 提供配置项允许恢复「人在就一直录」的旧行为。
- **编码**：优先检测可用的硬件编码（NVENC / QSV），不可用则回退现有路径；
  以基准决定是否切换，不为了硬件编码牺牲兼容性。
- **码率与分辨率**：录像允许低于抓拍分辨率（例如 720p、15fps）；
  抓拍保持原分辨率。
- **存储预算**：GUI 与 `rw storage` 显示「按当前策略还能录约 N 天」；
  保留 `keep_days` 与 `max_total_gb`，但清理顺序改为先删最旧事件片段。
- 预录环形缓冲的 JPEG 编码开销纳入基准；若占比明显，评估降低预录
  分辨率或帧率。

### 6.5 产品化与分发

- **安装器**：
  - 注册「登录时静默启动」计划任务（启动 guardian，而非 watcher）；
  - 任务启用失败自动重启；
  - 无窗口、无控制台闪窗；GUI 可选；
  - 安装后自动运行 **GUI 向导**（首次配置的主路径），并做一次
    「真在工作」验证：摄像头出画面、磁盘可写、推送测试送达、
    （可选）心跳测试成功；
  - `rw setup` 控制台向导保留为无界面/源码部署的降级路径；
  - GUI 向导至少包含：摄像头枚举与实时预览、本人注册、推送配置与测试、
    外部心跳配置与测试、开机自启状态确认；
  - 监控本身不依赖 GUI；GUI 关闭不影响已启动的监控。
  - 卸载保留 `config.local.yaml`、`data/`、事件库（沿用现有约定）。
- **首次使用**：向导路径覆盖「摄像头选择 → 本人注册 → 推送配置 →
  外部心跳 → 开机自启」，每一步都有成功/失败反馈，失败给出可操作的
  下一步，而不是只写日志。
- **诊断**：`rw diag`、健康快照、恢复通知、GUI 首屏状态
  （在线/停滞/上次重启原因/最后推送成功时间）。
- **文档**：
  - README 的「快速开始」改成面向陌生用户的路径；
  - 新增 FAQ：摄像头被占用、Windows 相机权限、杀毒软件误报、
    SmartScreen 提示、企业微信只支持内部群、必须保持登录状态；
  - 隐私说明：本机处理、哪些数据会离开机器、外部心跳只发送存活信息；
  - 升级说明：设置与数据保留、版本纪律。
- **更新**：沿用现有 `rw update`；注意 outbox/DB schema 迁移。
- **兼容性**：Windows 10/11 x64；per-user 安装；不要求管理员权限；
  摄像头隐私权限检查纳入向导。

### 6.6 平台边界（为未来 Linux 留口，不现在实现）

- 新增薄抽象层，集中以下能力，Windows 实现先行：
  `autostart`、`tts`、`system_volume`、`video_encoder`、
  `camera_backend`、`process_supervision`、`notification_transport`。
- 业务逻辑（rules、identity、outbox 状态机）不得直接调用
  `platform.system()` 或 Windows API。
- 现有 Windows 实现迁移到抽象层之下；行为不变，测试不变。
- 不为 Linux 预写空实现，也不引入跨平台依赖。

### 6.7 数据与兼容性

- 现有目录规则不变：`data/` 隐私、`var/` 可重建。
- 新增 `var/outbox/`（待投递媒体，可重建/过期清理）、
  `var/diag/`（诊断包）、`var/bench/`（基准结果）。
- DB schema 使用 `PRAGMA user_version` 做版本化迁移；
  迁移失败时保留旧库并报错，不静默重建。
- `config.local.yaml` 深合并规则不变；新增配置键必须有安全默认值，
  旧配置无需修改即可升级。
- 现有 `notify.channel` 单值配置继续兼容，读取时转换为单元素渠道列表。

## 7. 测试策略

- 纯逻辑优先放 `rules.py` 或新的纯函数模块，保持离线可测。
- 新增测试：
  - outbox 状态机：重试、退避、去重、永久失败、过期、容量挤压；
  - 投递分类：哪些 HTTP 状态/异常可重试；
  - guardian 决策：重启阈值、退避、停滞判定（注入假 PID/假心跳）；
  - 录制策略：最大时长、冷却、本人在场截止；
  - 健康快照与退出码映射；
  - 配置迁移：旧单渠道 → 渠道列表；
  - 心跳调度：间隔、失败路径、不包含敏感字段。
- 故障注入：模拟断网、模拟推送 5xx、模拟进程被杀、模拟卡死
  （全部用注入而非真实网络/进程）。
- 现有 544 项测试必须全绿；`rw test --fast` 保持可用。

## 8. 里程碑与验收

顺序按所有者优先级；M2 可与 M1 并行。

- **M0 可观测性**：崩溃钩子、退出码、健康快照、日志轮转、`rw diag`。
  验收：人为制造异常时，日志与 health 能说明原因。
- **M1 守护与自愈**：guardian 管两个服务、重启历史、恢复通知、
  计划任务静默自启、启动自检。
  验收：杀掉 watcher/gallery 后自动恢复并留下原因；
  连续运行 7 天无「无解释退出」。
- **M2 投递层**：outbox、重试、多渠道、通用 webhook、外部心跳。
  验收：断网 10 分钟后恢复，积压消息 5 分钟内送达且不重复；
  整机失联由外部服务在配置的宽限期内告警。
- **M3 存储与录制策略**：最大片段、本人策略、硬件编码评估、存储预测。
  验收：同等使用强度下磁盘增长显著下降，且事件片段完整可播。
- **M4 推理性能**：基线与引擎决策；仅在数据支持下切换。
  验收：有前后对比报告；无收益则不切换。
- **M5 产品化收尾**：向导验证、FAQ、隐私说明、诊断包入口、托盘/状态可见。
  验收：一位没有看过仓库的 Windows 用户，按 README 完成安装并收到测试推送。
- **M6 平台抽象**：把 Windows 专属能力收进接口层。
  验收：行为与测试不变，业务层无新增 Windows 直接调用。

**总体成功标准**：

- 真实事件在正常网络下：文字通知 10 秒内、照片 30 秒内送达；
- 任何一次 watcher 退出都能回答「为什么」，且用户会收到恢复通知；
- 断网、重启、队列积压都不丢文字告警；
- 整机失联可被外部发现；
- 待机 CPU/RSS 有基线，优化有数据；
- 现有用户升级不需要重新配置。

## 9. 留给构建者的决定

- outbox 与 events 是否同库；具体迁移实现。
- 退出码与停滞阈值的最终取值（先用本文建议值，基准后调整）。
- 视频压缩/上传的具体队列并发与超时。
- 通用 webhook 的 JSON 字段细节与媒体内联策略。
- autostart 的检测顺序与降级实现（计划任务 → HKCU Run + VBS），
  以及旧入口清理方式；要求零闪窗、无双实例。
- GUI 向导的摄像头枚举方式（索引探测 + 预览）与失败提示。
- 基准工具的具体参数矩阵与报告格式。
- 是否为 `rw diag` 增加一键上传（默认不上传，只生成本地 zip）。
- 托盘图标是否在本阶段实现；如果实现，必须可选且不阻塞主流程。

```yaml
  heartbeat_start_url: ""     # 可选；guardian 启动时 ping

record:
  max_clip_seconds: 180
  owner_present_max_seconds: 600
  cooldown_seconds: 30
  target_height: 720
  target_fps: 15

  engine: auto           # auto | cv2 | onnxruntime
  input_size: 640        # 目前只允许 640；资产是固定形状
  interval_frames: 1
```
