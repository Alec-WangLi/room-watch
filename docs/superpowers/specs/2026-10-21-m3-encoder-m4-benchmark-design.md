# M3 编码器切换与 M4 基准决策设计

- 日期：2026-10-21
- 状态：待所有者确认
- 适用范围：Windows 桌面版；不改变产品形态（本机常开主机 + USB 摄像头）
- 上游文档：`docs/superpowers/specs/2026-10-19-reliability-productization-design.md`（M3/M4）

## 1. 背景与意图

M3「录制/存储」在 0.1.17 已经交付了单段上限、本人在场策略、容量预测与
保留策略；唯一没做的是**按当年的基准数据切换编码器**。0.1.17 的实测是
720p@10fps、120 帧合成画面：

| 编码器 | 方式 | ms/帧 | MB/分钟 |
|---|---|---:|---:|
| avc1 | cv2.VideoWriter | 6.9 | 133.3 |
| h264_mf | ffmpeg（Media Foundation） | 4.0 | 59.6 |
| h264_nvenc | ffmpeg（NVIDIA） | 6.4 | 26.7 |

录像管线一直停留在 avc1，磁盘占用约为 h264_mf 的两倍。M4「推理性能」
只交付了 `rw bench-detect` / `rw bench-encode` 两个测量工具，没有引擎对比，
也没有决策记录。0.2.1 的「本人在场降频推理」是计划外的性能优化，不替代
M4 的引擎决策。

本设计的意图：这一轮把 M3 收口（按数据切换录像编码器），并完成 M4 的
基准与决策（可能结论是继续使用 cv2.dnn）。

## 2. 目标

### M3

- 录像默认走 ffmpeg 编码器，优先 `h264_mf`，不可用时按 `h264_nvenc`、
  `libx264` 的顺序回退；ffmpeg 不可用或连续失败时回退现有 cv2 avc1。
- 用户可见行为不变：预录开头、时间戳叠字、音轨合并、分段续录、相册回放、
  录像推送、事件库关联都与现在一致。
- 真机同一场景下每分钟体积至少下降 40%；编码耗时不得高于 avc1；
  正常情况下不出现新的丢帧。
- 编码器选择可配置，失败有日志与状态可查，不静默降级。

### M4

- 增加 ONNX Runtime 推理后端的**可选实现**（不默认捆绑、不改变默认路径），
  用于和 cv2.dnn 做同帧、同线程数、同输入尺寸的对比。
- 给出本机基准报告：延迟（p50/p95）、CPU 核数、检测结果一致性。
- 按上游文档的决策门：CPU 或延迟改善 ≥20% 且检测不回退，才考虑切换；
  否则明确记录「维持 cv2.dnn」并关闭 M4。
- 本机 0.2.1 已把「本人在场」的推理降到每秒 2 次；本轮基准必须在
  **与生产一致的线程数**下测量，避免多核全开造成假数据。

## 3. 非目标 / 反目标

**非目标**

- 不降低录像分辨率或帧率（`record.target_height/fps` 草案本轮不做）。
- 不默认捆绑 ONNX Runtime / CUDA / OpenVINO；不改变安装包构成。
- 不做 M6 平台抽象、不做托盘。
- 不为了追求体积更换为 HEVC（浏览器与兼容性风险，另议）。

**反目标（能跑也算失败）**

- 录像降级后留下打不开或没有音轨的片段。
- ffmpeg 失败后静默继续、用户不知道录像已经回到 avc1。
- 为了省 CPU 改变检测语义或漏报增加。
- 把 ONNX Runtime 变成必需依赖，导致安装包膨胀或旧机器装不上。

## 4. 已定决策（来自所有者）

- 本轮同时收口 M3 与 M4；M4 的验收按上游文档：**有对比报告，无收益则不切换**。
- 优先级仍是稳定性 > 性能 > 功能数量：录像后端必须可回退，先验证再改默认。
- 版本号只动修订号（本轮目标 0.2.2），发版与打 tag 仍需所有者同意。

## 5. 设计

### 5.1 录像写出后端

在 `roomwatch/recorder.py` 内部抽象一个最小写出接口（不新增包级依赖）：

```text
open(path, size, fps) -> bool
write(frame) -> None      # 失败抛异常
close() -> None
description: str          # 例如 "h264_mf (ffmpeg)" / "avc1 (cv2)"
```

两个实现：

1. **Cv2Writer**：现有 `cv2.VideoWriter` 逻辑原样迁移，编码器链
   `record.codec` → `CODEC_CHAIN` 不变。
2. **FfmpegWriter**：`ffmpeg -f rawvideo -pix_fmt bgr24 -s WxH -r fps -i -`
   从 stdin 吃帧，输出 mp4。参数基线沿用 `benchcodec.bench_ffmpeg`
   的命令，补 `-movflags +faststart` 与 `-pix_fmt yuv420p`。
   - stdout 丢弃；stderr 由独立线程持续读取并保留最后若干行，避免管道写满
     导致 ffmpeg 卡死。
   - `close()` 先关 stdin，等待进程退出（复用现有 `join_timeout_seconds`，
     默认 8 秒），超时则结束进程并记录 stderr 尾部。
   - Windows 下 `CREATE_NO_WINDOW`，不闪控制台。
   - 一帧都没写成功时删除空文件；写线程异常时记录 `last_error`。

`Recorder` 的队列、后台写线程、预录缓冲、`_fit()` 尺寸统一、`written` /
`dropped` 计数与 `last_pre_frames` 语义保持不变。音轨合并继续走
`-c:v copy` + `adelay`，因此新后端产出的 mp4 必须能被 ffmpeg 正常识别为
H.264 + yuv420p。

### 5.2 选择与回退

- 新增配置 `record.encoder: auto | cv2 | ffmpeg`，默认 `auto`。
- 新增配置 `record.ffmpeg_encoder: auto | h264_mf | h264_nvenc | libx264`，
  默认 `auto`。
- `auto` 的选择顺序：`h264_mf` → `h264_nvenc` → cv2 avc1。
  **不把 `libx264` 放进 auto**：它是软件编码，没有基准数据证明不慢于 avc1，
  而 M3 的验收要求编码耗时不得变差。需要时由用户显式配置。
- **启动时真编一帧再决定**（构建者判断）：`-encoders` 只能证明编码器编译进了
  ffmpeg，不能证明驱动/系统真的能用（`h264_nvenc` 可能被驱动拒绝，
  `h264_mf` 在 Windows N 版或 RDP 会话里可能失败）。每个 watcher 进程在
  第一次录像前做一次性探测：按候选顺序各编 3 帧 256×144 的合成画面到临时文件，
  第一个成功的写进缓存；全部失败则本进程固定用 cv2。探测耗时在毫秒级。
  （64×64 会被 NVENC 以 Invalid argument 拒绝，所以用 256×144。）
- 显式配置了 `ffmpeg_encoder` 时，先验证该编码器；失败后按 auto 顺序回退。
- 编码器探测（`-encoders` 解析）只用于快速排除明显不存在的名字；
  解析失败不当作致命错误，直接进入 cv2 回退。
- 状态文件新增 `video_encoder`（本段实际使用的编码器）与 `video_encoder_error`
  （最近一次失败原因），便于真机验证与诊断；GUI 不依赖这两个字段。

### 5.3 失败处理（构建者判断）

**启动失败**：当前候选进程没起来或第一帧写不进去，就换下一个候选；
全部 ffmpeg 候选都失败才回退 cv2。只有「一段录像里所有 ffmpeg 候选都失败」
才计入熔断；连续 2 段如此，本进程剩余时间不再尝试 ffmpeg。

**中途失败**：ffmpeg 被杀或自己退出时无法写出 mp4 索引（`+faststart` 在收尾时
写），留下的一定是坏文件。处理如下：

- 关闭并删除这一段视频，**不保留打不开的片段**；
- `Recorder.stop()` 返回 `None`，watcher 跳过音轨合并与录像推送，
  并把事件库中该事件的 `video` 字段清空（新增一个小的存储方法），
  相册只显示照片，不出现坏链接；
- 写一条结构化日志，并通过投递层发一条 `critical` 通知「录像中断，
  已回退」，同一进程内去重，避免刷屏；
- **不在同一事件里续录第二个文件**：现有 watcher 假设一个事件对应一个视频
  （`current_video`、单次音轨合并、单次 `push_video`、事件库单列）。
  扩展到多段是另一个设计，本轮不做。下一个事件会用 cv2（或探测通过的下一个
  编码器）正常录。
- 主循环、guardian 与停止协议不受影响；拍照与文字告警仍然送达。

### 5.4 配置与路径

```yaml
record:
  encoder: auto           # auto | cv2 | ffmpeg
  ffmpeg_encoder: auto    # auto | h264_mf | h264_nvenc | libx264
```

ffmpeg 路径复用现有音轨合并的解析规则：`record.audio.ffmpeg` 显式配置 →
分发包内 `tools/ffmpeg.exe` → PATH。如果录音模块里已有等价逻辑，抽成一个
共用函数，不要复制第二份。

### 5.5 M4：可选推理后端与基准

- 新增 `OnnxRuntimeDetector`（建议放在 `roomwatch/onnx_detector.py`）：
  - 惰性 `import onnxruntime`，未安装时只报「不可用」，不影响导入与启动；
  - 前处理/后处理复用现有 letterbox、解码、NMS 实现，保证与 cv2 路径同语义；
  - `detector.engine` 增加 `onnxruntime` 取值；`auto` 永远不自动选它。
- `rw bench-detect --engine onnxruntime` 对同一张图、同一线程数、同一
  `imgsz` 计时，输出 p50/p95 毫秒、CPU ms/帧与核数；同时跑 cv2 作为基线。
- 检测一致性：同一图片两套后端的框数量、类别、置信度与 IoU 对比；
  允许数值误差（置信度 ±0.02，框 IoU ≥0.95），不一致即判失败。
- 基准报告写入 `docs/bench-2026-10-21-m3-m4.md`，包含机器信息、命令、
  原始数字与结论。
- 决策门：CPU 核数或 p95 延迟改善 ≥20%，且一致性通过，才在报告中建议切换；
  本轮**不把 onnxruntime 打进安装包**，是否捆绑另行取得所有者同意。
- 轻量 `rw bench`：采样正在运行的 watcher 的 `health.json`（不占摄像头），
  输出 CPU 均值/峰值、RSS、连续错误、帧新鲜度；用于空闲/事件时段的
  生产环境观测。推理延迟 p50/p95 由 `bench-detect` 提供。

### 5.6 验证

- 单元测试：编码器探测解析、后端选择顺序、显式配置优先、逐一尝试候选、
  回退 cv2、ffmpeg 启动失败与中途失败（注入假进程）、close 超时、
  熔断、状态字段、失败时清空事件库的 `video` 字段。
- 离线集成：用真实 ffmpeg 编 30 帧合成画面，再用 cv2 读回并确认帧数 > 0；
  生成一段静音 wav 走现有音轨合并，确认输出仍可读。ffmpeg 缺失时跳过。
  `rw bench-encode` 增加 `libx264` 一行作为数据（只测量，不进 auto）。
- 真机验证（构建者判断的覆盖范围）：
  - 默认路径：`auto` 实际选中 `h264_mf`，用手机播放一段“人走进房间”的视频
    触发一次非本人事件（避开本人在场策略），检查片段能在相册直接播放、
    有声音且时间戳对应、开头包含预录、每分钟体积相对 avc1 下降 ≥40%；
  - 强制切到 `h264_nvenc` 与 `libx264` 各录一段，确认同样可播
    （本机两个编码器都存在，可以真测；客户机上不可用时的回退由单测覆盖）；
  - 把 ffmpeg 路径指向不存在的文件，确认本段回退 cv2 且状态里能看到原因；
  - 中途杀掉 ffmpeg 由单测/注入覆盖，真机不刻意制造。
- 回归：全量 `rw test`；0.2.1 的本人降频行为不受影响（`OwnerInferenceThrottle`
  测试保持全绿）。

## 6. 里程碑收口

- **M3**：编码器切换 + 真机片段验证通过即收口；上游文档的
  「磁盘增长显著下降、片段完整可播」作为验收。
- **M4**：基准报告与决策落盘即收口；若数据不支持切换，结论写
  「维持 cv2.dnn」，不实施引擎切换。

## 7. 留给构建者的决定

- `h264_mf` / `h264_nvenc` 的具体码率与质量参数（先用编码器默认值，
  真机体积或画质不可接受时再调）。
- 熔断阈值的冷却窗口（当前定为同进程内不再尝试，是否要跨重启保留）。
- ONNX Runtime 的版本、session 选项与线程配置。
- `rw bench` 的报告字段与采样窗口；是否需要 JSON 输出以外的图表。
- 音轨合并与 ffmpeg 写出的进程优先级/超时细节。
