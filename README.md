# room-watch · 房间进入抓拍

用电脑自带摄像头持续看房间，识别到**人**就抓一张带时间戳的照片存本地，并推一条消息到手机。
全部在本机运行，视频不出机器、不上云。

## 为什么不是 Frigate / MotionEye

它们是出色的开源项目，但都假设你有一台 **Linux + Docker** 的常开主机，且摄像头走 RTSP。
在 Windows 上 Docker 跑在 WSL2 里，USB 摄像头无法直通（`usbipd-win` 对摄像头驱动支持很差）。

而这里的需求其实很窄——「有人进来，拍一张，告诉我」。为它搬一整套 NVR，80% 的复杂度是白付的。
所以本方案是**约 2400 行 Python + YOLO**（含语音播报、人脸检测、本地相册、响度处理），直接读本地摄像头。

如果你的情况变化了（比如添了常开小主机或 RTSP 摄像头），再去上 Frigate，那是更合适的选择。

## 快速开始

```bash
# 1. 装依赖
pip install -r requirements.txt

# 2. 确认摄像头画面角度（拍一张 preview.jpg 然后退出）
python watcher.py --probe

# 3. 试跑：只存档不推送，观察误报率
python watcher.py --dry-run

# 4. 正式运行
python watcher.py
```

第 2 步很重要。**摄像头对着哪里，决定了这个方案 80% 的效果。**
建议对着房门内侧，画面里能完整看到人走进来的上半身。对着天花板或只拍到门口一条缝，检测率会很差。

跑起来之后如果语音听着小，先查瓶颈在哪（代码侧已做到满刻度，剩下的往往是系统音量）：

```bash
python watcher.py --volume-check    # 主音量 / 默认输出设备 / 本程序音量
python watcher.py --ab              # 原始语音 vs 处理后的语音，直接听差别
```

## 配置推送

编辑 `config.yaml` 的 `notify.channel`：

| channel | 能发照片吗 | 说明 |
|---|---|---|
| `wxpusher` | 只能文字 | 微信搜 WxPusher 公众号，建应用拿 `AT_` 开头的 token，关注后拿 `UID_` |
| `serverchan` | 只能文字 | sct.ftqq.com 登录，复制 SendKey |
| `wecom_bot` | **能发图片** | 企业微信群机器人 Webhook，图片走 base64，不需要公网 URL |
| `none` | — | 只写日志，调试用 |

**关于照片和隐私**：WxPusher / Server酱 要显示照片，必须先把照片传到公网图床——
那等于把你的房间照片放到别人服务器上。所以默认设计是**微信只收文字告警，照片留本机**，
用下面的相册看。想让照片直达微信，就换 `wecom_bot`。

### 看抓拍照片

```bash
python gallery.py      # 打开 http://127.0.0.1:8765
```

只监听 127.0.0.1。要在手机上看，配合 Tailscale / frp / cpolar 等内网穿透，
**不要**把 `--host` 直接暴露到公网。

## 事件录像

一张静态照片能告诉你「有人来过」，回答不了「他进来之后干了什么」。
所以确认有人进入时会**同时录一段视频**，和抓拍同名归档：

```
captures/2026-10-17/
  ├─ 090310.jpg    抓拍（带时间戳）
  └─ 090310.mp4    录像（同一进入事件）
```

相册页会自动把两者配成一条：照片当封面，点开就能播全过程，
支持拖动进度条（为此相册自己实现了 HTTP Range，标准库不支持）。

### 录像覆盖哪一段

```
       预录 8s        录像主体                      收尾
  ─────────────┬──────────────────────────┬──────────┬───────
               │                          │          │
           触发确认                    到单段上限   人走了
          (ACTION_START)              (自动接下一段) (不再有人的第 20 秒)
```

- **预录 8 秒**：不等触发后才开录。视频开头是「推门走进来」那一刻，
  而不是人已经站定了才开始。实现上是主循环持续把最近 8 秒的帧
  以 JPEG 缓存在内存里（720p 约 10MB），开录时先倒进视频
- **不等抓拍完成**：一旦连续确认有人（ACTION_START）立刻开录。
  若等到出图那一刻（ACTION_FIRE），人早就走过镜头了
- **自动分段**：保洁待 20 分钟不会被 5 分钟掐断，而是到点接一个新文件继续录。
  一次在场最多录 30 分钟（`max_total_seconds`），到点即使人还在也停，
  防止有人赖一天把磁盘写满

### 编码与性能

| 编码器 | 真实格式 | 相册能播吗 | 实测速度 |
|---|---|---|---|
| **avc1**（默认） | H.264 | ✅ 浏览器原生支持 | 11~18 ms/帧 |
| mp4v | MPEG-4 Part 2 | ❌ 基本放不了 | 2.4 ms/帧 |

只能选 avc1。但 H.264 编码要 11~18 ms/帧，而 `camera.fps=10` 每帧只有 100ms 预算，
里面还扣着 YOLO 推理。所以录像走**独立后台线程**，主循环只做「把帧丢进队列」
这种纳秒级操作；实测喂帧耗时远低于 50ms。队列满时**宁可丢帧也不让主循环卡顿**——
录像掉几帧无伤大雅，检测被拖慢导致漏人才是真问题。

跑起来时日志里可能出现 `Failed to load OpenH264 library`，**可以忽略**：
那是 OpenCV 的 FFmpeg 后端在抱怨缺 `openh264-*.dll`，实际由 Media Foundation
后端接手并写入了真正的 H.264。写出的文件里能验出 `avc1` box。

### 音轨（录音）

录像默认带声音。画面走 OpenCV VideoWriter，声音用 sounddevice 单独录成 WAV，
收尾后再用 ffmpeg 把音轨并进 mp4（视频流 `copy`，不重编码，几百毫秒完成）。

**一个必须说清的对齐细节**：录像带 8 秒预录，视频开头是「人还没进门」——
但那一刻还没开始录音。所以合并时会用 ffmpeg `adelay` 给音轨补等长静音，
长度按**实际**预录帧数算（刚启动时缓冲没攒满，会短于配置值）。
不这么做，你听到的声音会整段晚 8 秒，对不上嘴型。

| 配置 | 说明 |
|---|---|
| `record.audio.enabled` | 关掉就是无声录像 |
| `record.audio.device` | `null` 用默认麦克风 |
| `record.audio.samplerate` | 16000 够用，体积只有 44.1k 的 1/3 |
| `record.audio.keep_wav` | `true` 保留中间 WAV（调试用） |
| `record.audio.ffmpeg` | ffmpeg 不在 PATH 时写绝对路径 |

没有麦克风、被别的程序独占、或者没有 ffmpeg 时，**只影响音轨**：
视频照常录，失败原因写进日志，绝不吞掉录像。

> **录音比录像敏感**——它记录的是对话内容。建议在门口明示「本区域有监控录像及录音」，
> 保留期不要设太长。

### 磁盘占用

720p / 10fps 实测约 **1.5 Mbps**，即 **每分钟约 11MB**：

| 场景 | 录像长度 | 占用 |
|---|---|---|
| 保洁进来转一圈 | 约 1~2 分钟 | 11~22 MB |
| 保洁认真打扫 | 20 分钟（分 4 段） | 约 220 MB |
| 一次在场上限 | 30 分钟 | 约 330 MB |

`snapshot.keep_days: 30` 是按天清理，但它管不住「今天有人来了一整天」——
一天之内照样能写出几十 GB。所以还有第二道闸门，按**体积**算：

| 配置 | 默认 | 作用 |
|---|---|---|
| `storage.max_total_gb` | 20 | 抓拍+录像+音频总上限，超了按最旧优先删。0 = 不限 |
| `storage.min_free_gb` | 3 | 磁盘剩余低于这个值，额外逼近清理到上限的一半 |
| `storage.check_minutes` | 10 | 多久检查一次 |
| `storage.protect_seconds` | 300 | 最近 5 分钟内写过的文件不删（可能正在录） |

查当前占用：

```bash
python watcher.py --storage
```

它会告诉你总占用、容量上限、磁盘剩余、最旧和最新文件，以及按类型（jpg/mp4/wav）的分布。

清理只删自己产出的 `.jpg/.mp4/.wav`，**目录里别的文件一概不碰**，
删空的日期目录也会一并收掉。

> **改完要重启才生效。** 运行中的 watcher 不会热加载 `config.yaml`，
> 旧的相册进程也认不出新代码（尤其是 Range 支持）。重启监控前先 Ctrl+C 或
> 关掉对应的终端；摄像头同一时刻只能被一个进程占用。

## 人脸识别：区分「你」和「别人」

**要解决的问题**：人脸**检测**只回答「这里有没有脸」。你坐回电脑前，检测器照样认为有脸，
于是监控把你当访客抓拍、播报、推送——实测一晚上 7 张抓拍里 6 张是本人在桌前。

要区分「是谁」，必须做人脸**识别**（1:1 比对），这是完全不同的模型。

### 先注册你自己的脸

```bash
python watcher.py --enroll                     # 正对镜头，自动采 12 张
python watcher.py --enroll-from 某张正脸.jpg    # 或者用一张已有的清晰照片
```

注册结果存在 `identity/owner.npz`：一个 128 维特征向量，**不是照片**。
它没法还原成图像，所以模板本身不构成额外的隐私风险。

（采集时只接受「画面里恰好一张脸」——多张可能是拍到了别人，混进模板就坏事了。）

### 验证识别准不准

```bash
python watcher.py --whoami captures/2026-10-17/230913.jpg
```

输出会告诉你是本人 / 他人 / 认不出，以及相似度数值。

### 识别之后的行为

| 判定 | 抓拍 | 录像 | 语音 | 推送 |
|---|---|---|---|---|
| 本人（已注册且认出来） | ❌ | ❌（已开录的会删掉） | ❌ | ❌ |
| 他人 | ✅ | ✅ | ✅ | ✅ |
| 认不出（背影 / 侧脸 / 太远） | ✅ | ✅ | ✅ | ✅ |

最后一行来自 `identity.unknown_policy: alert`（默认）——**看不清脸就当访客**，安全优先。

如果你更想要「自己安静」，改成 `ignore`：认不出时也静默。
代价很明确：**保洁如果一直背对镜头，就不会被记录**。

### 三个不该踩的坑

1. **模型缺失时不会静默**。SFace 模型不存在或损坏，识别自动关闭，
   行为退化成「所有人都是访客」——绝不会把陌生人当成主人放过去。
2. **「本人」状态会在画面空了之后解除**。不解除的话，你自己进来一次之后，
   接下来所有人都会被当成你——这是最危险的失效模式，代码里专门处理了。
3. **阈值比官方更严**（0.45 vs 官方 0.363）。认错人的代价（把保洁当你、直接免报）
   远大于多认一次的代价。

### 技术选型：为什么用 OpenCV 自带的 SFace

`cv2.FaceRecognizerSF` + `face_recognition_sface_2021dec.onnx`（37MB）。
不用 `face_recognition` / dlib 是因为那两个在 Windows 上要编译，坑极多；
而 SFace 的输入恰好就是 YuNet 输出的 15 维人脸框（含 5 个关键点），两个模型天然配对。

> **一个静默出错的细节**：`alignCrop()` 需要**原图**和**原图坐标系**的关键点。
> 人形框里裁剪出来的坐标必须补回偏移量，否则对齐出来的脸是错位的、特征全废，
> 而且它不会报任何错——只会让你认错人。

## Windows 上必须做的一件事：别让它睡着

你说电脑基本常开——但"常开"和"真的不睡"是两回事。合盖、屏保、空闲休眠都会让监控静默失效，
而保洁往往正好在你离开房间时进来。

```
设置 → 系统 → 电源 → 屏幕和睡眠
  ├ 使用电池：从不
  └ 接通电源：从不
设置 → 系统 → 电源 → 其他电源设置 → 选择关闭盖子的功能 → 关闭盖子时：不采取任何操作
```

设完之后，**拿手机拍一下自己走出房间再走进来**，看 `captures/` 里有没有图。
没跑通之前别假设它工作。

## 语音提示

检测到人（且看清脸）时，对着现场说一句「您已进入监控区域，请注意」。

- **完全离线**：走 Windows 自带的 SAPI5 语音（中文是 Microsoft Huihui），不联网、不需要 API key
- **异步播放**：语音在后台线程播，不会卡住检测主循环
- **只在看清脸时出声**：`voice.require_face: true`，避免对着背影或路过的半个人说话
- **一波人只说一次**：人离开画面 3 秒后才重新武装，不会对着坐在电脑前的你循环播报

人脸检测用 **YuNet**（OpenCV 5 已不再自带旧的 Haar 级联文件），模型 230KB 放在 `models/`，
同样离线。只在 YOLO 框出的"人"的区域里找脸，又快又不容易把墙上的图案误判成脸。

### 为什么"把 volume 调到 1.0"没用

实测 SAPI5 中文语音的输出电平：

| 引擎音量 | 峰值 | 响度(RMS) |
|---|---|---|
| 1.0（上限） | **-11.8 dBFS** | -30.6 dBFS |
| 0.3 | -29.3 dBFS | -48.1 dBFS |

注意第一行：**引擎开到最大，峰值也才 -11.8 dBFS**，离满刻度还差将近 12 dB。
这段动态范围是引擎自己没用上的，系统音量拉到 100% 也补不回来。

所以本方案播的不是引擎原始输出，而是**先合成、再做一遍振幅**：切头尾静音 → 高通滤掉小喇叭
放不出的低频 → 压缩把弱音节抬上来 → 峰值归一到 -1 dBFS → 限幅保底。实测效果：

```
峰值  -11.8 -> -1.0 dBFS   (+10.8 dB)
响度  -30.6 -> -15.2 dBFS  (+15.4 dB)
时长  3.63s -> 2.77s（切掉了头尾静音）
```

处理结果缓存在 `voice_cache/`，里面还有一份 `.json` 记录实测增益——"变响了多少"是能翻出来
核对的数字，不是一句"我调过了"。改了文案、语速或响度参数会自动重新生成。

```bash
python watcher.py --say       # 试听处理后的版本，并打印增益
python watcher.py --say-raw   # 试听未处理的原始版本
python watcher.py --ab        # 先原始、再处理，直接听差别
```

### 另一个更隐蔽的天花板：系统主音量

代码里做到满刻度只解决一半问题。如果 Windows 主音量本身很低，下游会再砍一刀：

```
代码侧：-11.8 dBFS ──处理──> -1.0 dBFS          (+10.8 dB)
系统侧：主音量 10% = 衰减约 20 dB   ← 这才是「怎么调都小」的主因
```

所以提供了查询与保底：

```bash
python watcher.py --volume-check       # 列出主音量、默认输出设备、各应用音量
python watcher.py --volume-set 70      # 手动设成 70%（永久生效）
```

`config.yaml` 里还可以让监控**运行期间自动保底**：

```yaml
voice:
  ensure_system_volume: 70      # 低于 70% 就抬上来；0 = 完全不碰系统音量
  restore_system_volume: true   # 退出时还原成启动前的音量
```

只在当前音量偏低时才动手，不会去压低本来就很大的音量。退出（含 Ctrl+C）会还原；
**进程被强制杀掉时不会还原**，此时用 `--volume-set` 手动改回去即可。

## 怎么确认它还在跑

一个安静挂掉的监控，和没装是一样的。所以有三层确认：

**1. 心跳推送（最重要）**
`heartbeat.interval_minutes: 30` —— 每 30 分钟推一条「监控在线」。
这是 dead man's switch：**你不是靠收到心跳确认正常，而是靠"该来的心跳没来"判断它挂了。**

**2. 随时查询**
```bash
python watcher.py --status
```
```
状态        : 在线
已运行      : 1h23m
最后画面    : 2026-10-16T15:23:03（4 秒前）
摄像头      : 正常
今日抓拍    : 1 次
```

**3. 相册页顶部状态条**
打开 `http://127.0.0.1:8765`，第一行的绿色「在线」/ 红色「已停止」徽章就是实时状态。

判定依据是**最后画面距今多久**（默认超过 120 秒算停止），而不是文件里记录的状态——
因为进程被强制杀掉时，它留下的最后一份状态永远写着"正常"，照着读就会把死掉的程序报成在线。

### 摄像头掉线自愈
读帧连续失败 10 次会自动重新打开摄像头（常见于 USB 松动、驱动抽风、被其它程序抢占）。

## 长期运行的可靠性：守护进程

监控自己能处理不少故障（读帧失败重连、摄像头掉线重开），但救不了**进程整个没了**：
Python 抛了未捕获异常、被系统 OOM 掉、句柄耗尽、误关窗口。
进程一死摄像头就没人读了，而你正在外面开会。所以要有一双外面的眼睛：`guardian.py`。

### 判据

| 现象 | 判断 | 处理 |
|---|---|---|
| PID 存活 + 心跳新鲜 | 正常 | 不动 |
| PID 存活 + 心跳停摆超 5 分钟 | 卡死 | 连续确认 2 次后杀掉重启 |
| PID 不存在 | 崩溃 | 立刻重启 |
| 重启后马上又挂 | — | 退避：1 → 2 → 4 → 8 → 15 分钟（封顶） |

两个刻意的设计：

- **「卡死」不立刻杀**。摄像头重连、模型首次下载都会让心跳停顿一两分钟，
  误杀一个正在自愈的进程比等它两分钟更糟。
- **重启带退避**。如果摄像头被别的程序独占，无脑重启会变成每分钟拉起一次的
  恶性循环，刷爆日志还占 CPU。

### 怎么用

```bash
# 方式一：双击这个（守护 + 监控一起管起来，关窗口只停守护，不动监控）
start-with-guardian.bat

# 方式二：单独跑常驻守护
python guardian.py

# 看守护状态、累计重启次数、最近动作
python guardian.py --status

# 只检查一次（幂等，给计划任务用）
python guardian.py --once
```

### 开机自启（需要你亲手执行）

计划任务属于持久化自启，必须由你授权创建。右键 `install-autostart.ps1` →「使用 PowerShell 运行」，
它会建两个触发器：**登录时** + **每 3 分钟**，跑的正是 `guardian.py --once`。

幂等是关键：监控活着时它什么都不做，所以跑 100 次和跑 1 次效果一样。

卸载：`Unregister-ScheduledTask -TaskName RoomWatchGuardian -Confirm:$false`

### 守护自己的并发保护

常驻守护和计划任务可能同时触发，两个都想重启就会撞车。所以真正动手前要拿文件锁
（`guardian.lock`）；拿不到说明别人在干活，本轮直接退出。
锁文件里写的是 PID，所以**上个进程崩了留下的陈旧锁能被识别并清理**——
这点很重要，否则守护会永久失效。

## 隐私与合规

这是监控他人，不只是技术配置：

- 摄像头放明处，避开床铺、卫浴
- 只存本地，保留期默认 30 天自动清理（`snapshot.keep_days`）
- 若是酒店 / 长租公寓 / 公司宿舍，先确认住宿条款或管理规定
- 保洁是工作人员，知会一声通常更体面，也能避免误会

## 调参

| 现象 | 改哪个 | 怎么改 |
|---|---|---|
| 光影、窗帘也报警 | `detector.conf` | 0.55 → 0.65 |
| 有人进来却没抓到 | `detector.conf` | 0.55 → 0.45 |
| 一个人在房间里反复推送 | `detector.cooldown_seconds` | 90 → 300 |
| CPU 太吵 | `camera.fps` | 10 → 5 |
| 要更准、愿意多花算力 | `detector.model` | `yolov8n.pt` → `yolov8s.pt` |
| 摄像头打不开 | `camera.index` / `camera.backend` | 试 0/1/2；`dshow` → `msmf` |
| **语音还是嫌小** | `voice.loudness.ratio` | 3.0 → 4.0（更响，但更"平"）；先跑 `--volume-check` 确认系统音量不是瓶颈 |
| 语音太"平"、听着不自然 | `voice.loudness.compress` | `true` → `false`，改用纯归一化 |
| 别再动系统音量 | `voice.ensure_system_volume` | 70 → 0 |
| 想看点完整过程 | `record.enabled` | `false` → `true`（重启后生效） |
| 视频开头太晚，人已站定 | `record.pre_roll_seconds` | 8 → 15（内存约 10MB/10 秒） |
| 录像太长、占磁盘 | `record.max_seconds` | 300 → 120（单段长度，超出会自动接下一段） |
| 保洁打扫要录全程 | `record.max_total_seconds` | 1800 → 3600（一次在场总上限） |
| 人一走录像立刻断 | `record.idle_stop_seconds` | 20 → 60（离开画面后仍接着录） |
| CPU 吃紧、录不动 | `camera.fps` 或 `record.pre_roll_seconds` | 降帧率；预录编码实测仅 0.8ms/帧，通常不是瓶颈 |
| 录像看着卡顿/丢帧 | `record.queue_size` | 120 → 240（给编码线程更大缓冲） |

## 独立运行 / 开机自启

**出门前双击 `start-room-watch.bat`** —— 它不依赖任何对话窗口或终端，
关掉终端也照样跑，日志写进 `watcher.log`。

开机自启：Win+R 输入 `shell:startup`，把 `start-room-watch.bat` 的快捷方式放进去。

注意别同时启动两份：摄像头只能被一个进程占用，后启动的那个会打不开。

## 检测逻辑：为什么不是"一有人就拍"

1. **连续 3 帧确认**：单帧误检（光影、反光）不触发
2. **挑最好的一张**：确认进入后再看 8 帧，选人最大、最居中、不贴边的那帧
3. **90 秒冷却**：保洁待 20 分钟，你只收到 1 条，不是 200 条
4. **本人在电脑前不推**：读 Windows 键鼠空闲时间，避免给自己发自己的照片
